## Requirements Drill — Flight Search Aggregator

### What He Wrote

**FRs:**
1. Search flights src-dest, show multiple airlines results
2. Sorting by price
3. Redirect to airline website when user wants to book

**NFRs:**
1. High availability (99.9%) ~8.6 hrs downtime/year
2. Low latency (<200ms) display of flights across airlines
3. Strong consistency for booking flights

### Scores

**FRs: 3/5**
- ✓ Core happy-path: search + redirect to book
- ✓ User-action focused, no implementation details
- ✗ No edge actions (filter by stops/time/airline, round-trip vs one-way, save/price alert)
- ✗ No out-of-scope block (hotel, car rental, seat selection)

**NFRs: 2/5**
- ✗ Scale: no DAU stated, no QPS derived
- ✗ Latency: `<200ms` stated but no p99 qualifier; 200ms also too aggressive for multi-airline API fan-out
- ✓ Availability: 99.9% + downtime calc (improvement — self-initiated this time)
- ✗ Consistency: booking side only (strong), search side skipped (should be eventual)

**Time: 3:48 — needs work (target <2:30)**

### Ideal Block (for comparison)

**FRs:**
1. Search flights by src, dest, date, passengers (one-way / round-trip)
2. Aggregate and display results from multiple airlines sorted by price, duration, stops
3. Filter by stops, airline, departure time window
4. Redirect user to airline/OTA site to complete booking
5. Save a search / set price alert for a route
6. **Out of scope:** hotel/car rental, seat selection, payments, loyalty points

**NFRs:**
> Scale: 50M DAU, 5 searches/day/user → ~2,900 QPS reads; bookings ~1% → ~29 QPS writes.
> Latency: search results p99 < 500ms (aggregating external APIs — 200ms too aggressive given network fan-out).
> Availability: 99.9% — ~8.7 hrs downtime/year; acceptable since booking happens on airline site.
> Consistency: eventual for search results (stale prices OK within ~60s), strong for saved searches/alerts.
