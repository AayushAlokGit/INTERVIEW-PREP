### Q3: A mistake with real consequences
**Theme:** Handling failure / mistakes
**Story deployed:** S001 (Zero-Downtime Config Migration). Correct story — the lead story and the right reach for this question. But the recovery mechanics contradicted themselves mid-answer, and he walked directly into the "keep the recovery physics straight" trap.

**Interviewer:** Tell me about a time you made a mistake that had real consequences. What happened, and what did you do?

**Aayush:** At Microsoft I was part of the Dynamics 365 Sales team working on the Sales Premium feature, which involved microservices deployed across different geographies. These microservices were dependent on config stores. Some context on the deployment structure at Microsoft: there are geo-level deployments and island-level deployments — a geo has multiple islands within it. Our microservices were deployed at island level while the config store they depended on was deployed at geo level. So multiple island microservices in a geo depended on a single geo-level config store resource. That was a single point of failure for an entire geo. So there was a need to migrate from Azure Table Storage — the previous geo-scoped config store — to a newer offering, PPMS, which was Azure Cosmos DB based. That allowed island-level deployment scope and also added a COGS reduction of $156,000 per year. I was in charge of this migration. I wrote a background service to perform it — it would transport data from Azure Table Storage to PPMS, and after all the data had been transported it would insert a flag marking migration completion in Azure Table Storage. The way the code worked: writes kept flowing to Table Storage until the migration flag had been inserted. The code had checks before writing or reading from the config store — they'd check if the migration flag had been inserted in Table Storage, and then reads and writes would flow to PPMS. I made the code changes and started the rollout progressively, from lower-traffic geos to higher-traffic geos. This was all feature-flag controlled, so I could start or pause the migration by toggling the feature flag. When my code changes were in the lower-traffic geo, I turned on the feature flag to run the migration. I noticed data flowing from Azure Table Storage to PPMS, the Table Storage being emptied, and finally the data reflecting in PPMS. After the migration was done and the completion flag inserted, after 15–20 minutes I noticed an anomaly — there were still writes coming into Azure Table Storage. This was an issue; I had expected all reads and writes should now go to PPMS. I investigated and found a particular write path in the code where the flag check had not been added, so writes were still flowing to Table Storage instead of PPMS. This was causing a data consistency issue — new writes from all other places in the code would go to PPMS, but writes and reads from that buggy area of the code would go to Table Storage. The data would eventually diverge if that wasn't fixed. So I turned off the feature flag to stop the migration. Now all the writes and reads would again go back to Azure Table Storage. But now there was a data consistency issue — since my migration service had deleted data from Azure Table Storage, there was data loss. The data had been moved from Azure Table Storage to PPMS. So what I had to do was move the data back manually — copy data from PPMS and fill back Azure Table Storage. I reported this issue to my manager. My manager said I needed to pause the migration to recover the data loss. I recovered the data loss, I fixed the bug, and then the migration continued and executed successfully. There was no impact since I caught the bug within 15–20 minutes. Luckily there was no customer impact, and the data loss which had occurred due to the migration deleting the data from Azure Table Storage was recovered quickly as I copied it from PPMS. So luckily there was no customer-facing impact.

**Follow-up 1 (physics probe):** I want to slow down on the recovery, because I don't think the mechanics you just described work. You said the data loss happened because the buggy write path kept writing to Table Storage *after* the migration had already drained and deleted it — so those writes were landing in a store nothing was reading from, and they were never synced to PPMS. Then you said you recovered by copying data from PPMS back into Table Storage. But PPMS never had those writes. So what exactly did you copy, and from where?

**Aayush:** The migration service had copied data from Azure Table Storage to PPMS and it deleted that data from Table Storage. So that data was missing. So that data had been copied back from PPMS to Azure Table Storage.

**Follow-up 2 (reconciliation probe):** Okay — so the data loss was that Table Storage had been *drained*, and flipping the flag off pointed everything back at an empty store. That's a different failure than what you first described. Let me test the edge: during those 15–20 minutes the flag was on, some writes went to PPMS through the correct paths, and some went to Table Storage through the buggy path. When you copied PPMS back into Table Storage, what happened to the writes the buggy path had already put there? Did you reconcile those two sets, or did one overwrite the other?

**Aayush:** [Writes] went to PPMS. Since I had directly copied — I had switched off the flag and copied data in PPMS directly to Azure Table — whatever writes that had gone to PPMS were now equivalent, they had also been transported to Azure Table. So PPMS was empty finally, and Azure Table [held] all the data.

*(Never addressed the buggy-path writes or the reconciliation. Answer thinned out here. Also never mentioned the `ConfigStore` abstraction — the actual root-cause fix and the story's earned insight.)*
