**Interviewer:** Tell me about the largest-scale or highest-stakes thing you've personally driven — something where the scope was bigger than what you'd normally be handed at your level. What was it, and what did you actually own?

**Aayush:** At Microsoft, there was a company-wide initiative to protect the cloud resources owned by a team from data exfiltration risks. I was assigned to protect the resources owned by our team, by my manager. We owned 100+ resources across 23 global subscriptions. The resources to be protected were things like storage accounts, Key Vaults. The way they were to be protected: they were supposed to be associated with Network Security Perimeter resources via NSP traffic profiles. So a resource was associated with the profile, and the profile was associated with a perimeter resource. I had to design the NSP profile architecture, and I had to own the deployment of the resources across all the subscriptions that we own, as well as the subsequent monitoring of the incoming and outgoing traffic to these resources. Finally, I was also required to specify the access rules that would be enforced on the traffic profiles, and the rules specified for the traffic profiles would be enforced on the resources. Here I faced a design decision. I could have one profile and link all the resources to that profile, or I could have one profile for each resource. The deciding factor was that the rules would be enforced on the profile, and they would be enforced on all the resources associated with one profile. So if there was only one profile, then all the varying traffic patterns could not be captured. So I decided to investigate the code and found that different kinds of resources had different traffic patterns. So I needed multiple traffic profiles to cover the various traffic patterns. I also documented this decision of designing the profiles by considering traffic patterns. After I was done with designing, I deployed everything end-to-end in a test subscription to verify that everything was working fine — all the resources were associated with the profiles, and there were no issues. Then I coordinated with another senior engineer in my team who owned the deployment to production. I coordinated with them daily for the deployment of resources. Midway, while the deployment was ongoing, we encountered quota issues in a few geos where we didn't have quota for the necessary resources. So I raised requests in the Azure portal, and in order to unblock myself, I continued making progress in other geos. Finally, when the deployment was complete in all the geos, now was the time to monitor the traffic that was incoming and outgoing from the resources in order to decide what the access rules would be. So I turned on learning mode and monitored the traffic to note down the access rules. And finally, we enforced the access rules, and I verified that none of the existing features were breaking. The data was showing as it should. The numbers were showing up in the dashboards. The result was that I had successfully rolled out the NSP resource associations across 23 global subscriptions and 100+ resources and prevented data exfiltration risk. It also met Microsoft-wide security standards and gained visibility into the network traffic coming and going from these resources. One important learning I had was that before deciding the architecture, I actually got familiar with the system, and that helped me design a better architecture. If I had not gone through the code to identify the various traffic patterns, then my initial design of the profile would have been wrong.

### Q2: Most impactful thing shipped, and why
**Theme:** Impact & results — open story choice (tests story selection when he gets to pick)
**Story deployed:** S001 (Config Migration) — **fourth outing, and the wrong story for an impact question.** Justified impact with "I made a mistake and had to own up to it." **Interviewer:** Tell me about the most impactful thing you've shipped in your career so far — and I want to hear why you consider it the most impactful, not just what it was.

**Aayush:** At Microsoft, I was responsible for performing a data migration from one context to another. We were working with microservices which were deployed at island scope, and these were dependent on a geo-deployed config store. One geo had multiple islands within it. So multiple microservice deployments were dependent on a single config store resource. This was a single point of failure, and it also had higher COGS. So the requirement was to move from the geo-scoped Azure Table Storage to an island-scoped, Cosmos DB-backed config store, which was called PPMS. This would reduce the blast radius to an island, and it also had a nice COGS reduction of $156,000 per year. I was responsible for the migration. I had written a background migration service which would copy the data from Azure Table Storage to PPMS and insert a completion flag marking the migration as completed, and then finally delete the data from Azure Table Storage. This entire migration was controlled by a feature flag, and I was rolling out my changes from lower-traffic geos to higher-traffic geos. In the code paths wherever the data was being written to the config store, I had added the migration completion flag checks to ensure that if the migration flag was inserted in Table Storage, writes and reads should go to PPMS. So when I started the migration, I turned on the feature flag in a lower-traffic geo. The data had been migrated from Table Storage to PPMS, and then I noticed that the completion flag had been inserted, but then I noticed that the writes were still coming into Azure Table Storage. This was an issue. What I was expecting was that writes should now go to PPMS, since the flag was turned on. And the Azure Table Storage had been emptied. On investigating the code, I found out that there was a write path in the code where I failed to add the migration flag check, and this was still writing to Azure Table Storage. I panicked a bit, and I raised this issue with my manager, informing him that things had been broken. My manager gave me the feedback that the issue had occurred because in my migration design, I was doing copy, route, then delete — I was not verifying before performing deletion. This was the cause of the data consistency [issue]. So what he suggested was to pause the migration now and recover the data. And since the migration had been paused, now all the reads and writes would flow to Azure Table Storage, and we needed to recover data that had been copied to PPMS. And meanwhile, the writes that had come in from the buggy write path — they also had to be reconciled. So I did this, and finally data consistency was established. The data was made consistent by my efforts. There was no customer impact since I had caught this quickly. I was vigilant in my monitoring. And then I went back to the code and fixed it. So that such issues would not occur again in the future, I created a new interface called `ConfigStore` and all the reads and writes would now pass through this interface. And this interface's methods were used everywhere in the code. Finally the migration was completed successfully. This was my most impactful [project] because I actually made a mistake, I had to own up to my mistake, and then I had to do things quickly in a very stressful situation. And also, business-wise, I think it had a good impact of reducing COGS.

*(Recovery physics correct in a single pass for the first time in four rounds — flag on, Table Storage drained, buggy path still writing, escalate, recover from PPMS, and he volunteered the reconciliation of the buggy path's writes unprompted. Minor slip: stated the dangerous sequence as "copy, route, then delete" — that is the SAFE sequence. The dangerous one is copy → delete → route. He inverted his own earned secret.)*

**Aayush:** The $156,000 was the delta between what the Azure Table Storage cost and the PPMS cost. That was the delta between the costs.

**Follow-up 1b:** You've told me what it's a delta *of*. I asked something narrower: who computed it, and did anyone go back after the migration shipped and confirm the bill actually dropped by that amount?
